This checkout uses the ROOT repository ghosttrubel/city-and-us. No new Site, publication, APK rebuild or live database reset is part of this work. The existing uploaded backup remains in player_save_backups; automatic saving continues using its conditional updated_at contract.

Both are transactional and fail on conflicting new object names. The foundation checks deletion cascades rather than replacing existing foreign keys. Normal gameplay requires the game_connection RPC to return version 1; without it the source intentionally stays paused. Review saves remain isolated and make no online requests.
3. Enable Email authentication, confirmation and an actual SMTP sender. Test confirmation, recovery and expiry. Under Authentication → URL Configuration add the exact existing game root, http://localhost:3000/, http://127.0.0.1:3000/, the corresponding account-deletion.html URL, and com.cityandus.lagosstreet://auth/callback. Set Site URL to the existing public game root, never the Android asset origin. Keep standard confirmation/recovery templates; implicit email callbacks and PKCE OAuth codes are supported.
4. Google Cloud → APIs & Services → Credentials: create an OAuth Web application client, configure consent/test users, and register https://yhervptejlpgallfinro.supabase.co/auth/v1/callback as the authorized redirect URI. Supabase → Authentication → Sign In / Providers → Google: enable it and store that client ID and secret there only. The browser client has no Google secret. Android opens ACTION_VIEW in an external browser and accepts only the exact custom callback; PKCE verifier remains in the initiating device storage. Add verified HTTPS App Links once an owned domain is configured. Test cancellation, wrong/expired codes, cold return and background return on hardware before release.
5. Deploy supabase/functions/delete-account with its config.toml (gateway JWT checking disabled because the function itself verifies the bearer with Auth /user). Supabase supplies SUPABASE_URL, SUPABASE_ANON_KEY and SUPABASE_SERVICE_ROLE_KEY only in function runtime. Never put the privileged key in source, Git or browser files. Audit deletion cascades before enabling. The function deletes only the verified caller. It never accepts a target account ID from the client.
6. External deletion route is <existing game root>/account-deletion.html. It supports sign-in, password recovery, immediate deletion and a persisted request. Configure the store listing to that public URL when publishing is separately authorized. account_deletion_requests is the project-owner/service-role operational queue. A project owner must monitor it; requests do not pretend to be completed deletion.
7. Chat migration grants only participant reads and RPC mutation access. Enable Realtime publication only for chat_messages (migration adds this table). chat_reports is the restricted moderation queue: project owners in SQL Editor or a server using service_role only; players cannot read reports. Assign a human owner to review pending reports and deletion requests before inviting public users. No notification was sent by this implementation.

## Save and deletion handling

Pending saves and message outboxes are isolated by authenticated UUID. Guest and account stories keep their existing keys. A conflict retains both copies locally for export; timestamps are compared, never used to guess which divergent story the player wants. Account sign-out retains pending saves without uploading them under another account. Recovery/manual downloads are under Advanced settings. Imported review provenance remains excluded.

Account deletion removes the verified account and cascading profile/save/chat rows. Local cleanup targets only that account's story, recovery, pending save and message outbox on the current device; gallery media, guest saves and unrelated accounts remain. Other devices and exported files may still contain local copies and need erasure there. Messages by a deleted sender are removed; the other participant retains their own messages. Reports involving the deleted account cascade away. A deletion network timeout must be treated as unconfirmed; retry or use recovery/request tools.

## End-to-end review

Use three dedicated confirmed test accounts A, B and C and two browser profiles/devices. Start npm start with the configured migrations. Sign A in, accept guest migration once if needed, complete a paid action and wait for Saved. Disable network: movement and service timers pause, local progress stays. Reload while disconnected; reconnect and confirm the same progress syncs. Sign out, sign B in, and verify A's pending data never appears or uploads to B. In a second A device make a divergent change and reconnect the first; choose between both displayed copies and verify the untouched recovery export. Start a new story in A: the account and local Player ID remain; reset progress syncs as one snapshot. Test email recovery, Google cancellation/return and an expired session. Review URLs must issue zero Auth/Data API requests.

After chat is configured, look up B by public Player ID, exchange messages, paginate history, disconnect/retry a send and confirm exactly one message. Check Sent before recipient fetch, Delivered only after recipient acknowledgement, and Read only after the visible conversation is rendered. Block, unblock, mute and report; verify the restricted moderation row. With C's token directly query A/B messages and attempt chat_send/chat_ack into their conversation: reads must return no rows and mutations must fail. Run the supplied live security test with dedicated accounts, never production players. Delete one dedicated account after explicit confirmation and verify unrelated users remain.

## Release blockers

Live SQL/Edge Function deployment and three-account access checks, configured OAuth/SMTP, browser/native visual and modest-phone performance acceptance, a staffed restricted moderation/deletion queue, and live deletion verification remain required. Mock checks are labelled unverified live.

Online-only play is not economy authority. Money, job/reward payouts, spending/refunds, inventory, rent, ownership, vehicle permissions, property access, progression and movement are still client-authored solo snapshots. Before public multiplayer/economy these need authoritative server transactions, ownership/permission checks, replay protection and server ledgers. Elections and shared gameplay remain unimplemented. Chat does not make those systems authoritative.
